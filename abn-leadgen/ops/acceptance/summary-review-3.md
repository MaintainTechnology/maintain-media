# Independent summary review and capacity sample

8 September 2026 UTC. Reviewed `ops.summary.operational_summary` against R34/R35 using isolated PostgreSQL16 fixture schemas. This is a bounded review, not an overall spec or release verdict.

The first regression run reproduced one real failure: a frozen/exhausted historical budget month generated a current `budget_stop` although the current Brisbane month had zero usage. The implementation owner restricted the check and usage projection to the current Brisbane calendar month and labelled that scope. The rerun passed **5 tests in 19.92s**: current-month isolation, expired policy, completed suppression exclusion, pending propagation threshold/deduplication and cumulative-attempt/contact denominator integration. Tests now live in `tests/integration/test_summary_review.py` and `test_operational_summary.py`, so normal CI discovers them. Command: `uv run pytest tests/integration/test_summary_review.py tests/integration/test_operational_summary.py -q`.

That review also identified incomplete alarm input wiring. The parent subsequently assigned this reviewer to implement `ops.monitor`, observation ingestion and fixture alarm delivery. Its later test results are builder evidence, not an independent certification. Unknown classifier/hit-rate baselines, publisher mismatch clocks, external timer inventories and live backup/restore observations must remain explicit. Actual known source failures, publisher age, distinct comparable publication volume, member counts, local resource samples, current budget/policy, incomplete suppression propagation, CRM uncertainty, stale active-run heartbeat and native backup-drill status are projected from recorded facts. Explicit typed inventory ingestion handles additional measured inputs without inventing them.

## PostgreSQL sizing evidence

Command: `uv run python ops/db_wal_sample.py --rows 1000 --output ops/acceptance/db-wal-sample-1000.json`.

The sample used PostgreSQL16.15 on Windows11, Python3.12.12 and the frozen lockfile. It created an isolated generated schema, applied all 18 migrations available at sample start, then committed 1,000 synthetic promoted leads through actual service methods. This included canonical groups, source aliases, queue, identity, contact/provenance, licence, express-basis and audit/control rows. It measured **7,364,608 bytes** table/index growth. The cluster-global insert-LSN interval measured **77,261,496 bytes** of WAL, including concurrent activity. This is an upper bound for sample-generated WAL, not isolated attribution or retained WAL disk use. The exact schema was removed successfully; public and other agent schemas were untouched.

`db-wal-sample-1000.json` records per-table counts/index/table bytes, migration digests, timestamps, exact command, platform, revision and lock hash. `db-wal-sample-1000-script.py.txt` preserves the exact measured script hash; the runnable script subsequently received only type-narrowing assertions. The sample is not a 20.5M-row PostgreSQL replica, full workload sizing, host certification or production capacity admission. History length, larger encrypted payloads, CRM/worklist/outcome rows, backups and retained WAL still need workload bounds. The separate Parquet full-register benchmark is owned by the root and is not certified by this sample.
