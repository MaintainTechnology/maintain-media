## Findings requiring fixes

1. **P1 — A passing consent basis can have missing required evidence.** `001_foundation.sql:79–80` checks an express pass with `length(express_scope)>0`; NULL scope makes the entire check UNKNOWN, which PostgreSQL accepts. The inferred path similarly accepts SQL NULL limbs. `Service.basis` (`service.py:191`) has no explicit pass-shape validation, and inserts omitted express scope as SQL NULL. Such a row satisfies `gate`'s state/time/policy tests. This violates R21. Fix the schema with an outer `IS TRUE` or explicit NOT NULL predicates and require the exact approved inferred limbs or nonempty express scope plus source/time evidence at the service boundary. Add real PostgreSQL cases for omitted/NULL scope, SQL NULL limbs, false/unknown limbs, and a valid express pass without invented publication limbs. Do not edit an applied migration; add a corrective migration if already applied.

2. **P1 — Contact collection writes invented capture evidence.** `Service.add_contact` (`service.py:169–187`) always persists `robots_result='allowed'`, `terms_scope='reviewed capture'`, and a fabricated `restricted:<UUID>` object reference; its digest is only of the supplied excerpt. It neither accepts nor validates a captured object/digest/robots/terms result, nor invokes the collection capability gate before storing endpoints. A caller can create an apparently evidenced contact when collection is disabled or the crawl was incomplete. This violates R20/R27. Require an actual stored capture manifest tied to the precise lead/domain, containing full captured-content digest, object receipt, collector time/version, robots result and actual terms scope; verify it and collection gates before the atomic contact/provenance write. Unknown terms must stay unknown. Add failure cases for missing object, altered digest, denied robots and closed collection capability.

3. **P1 — Endpoint-only opt-outs have no downstream propagation or deletion schedule.** `Service.suppress` finds affected leads for endpoint tokens, but creates `deletion_job` and `propagation_outbox` entries only inside `for group in group_ids` (`service.py:406–412`). Endpoint-only calls leave that set empty. Local gate reads deny the endpoint, while previously exported copies receive no durable removal/block work or retention deadline. This violates R25/R29. Create endpoint-scoped propagation and cleanup work for all affected remote mappings without converting an endpoint-only restriction into unrelated whole-business suppression; preserve token-only jobs for as-yet-unknown leads. Test a shared endpoint on two distinct groups, already-exported CRM copies, retry, and later alias association.

4. **P1 — Phone candidates can export with unknown recipient locality/timezone.** `Service.gate` performs calling checks only under `if action` (`service.py:299–318`). A washed phone with no confirmed recipient timezone/locality is allowed by candidate export. R28 explicitly blocks phone eligibility until that ambiguity is reviewed. Require confirmed timezone/locality and applicable calendar coverage in the candidate branch; retain the actual time-of-day recheck immediately at consumption. The existing `compliance/calling.py` provides explicit IANA/approved-calendar primitives. Add candidate-level unknown timezone/locality/expired calendar tests and a confirmed positive case.

5. **P1 — Live key loading does not validate security invariants or retained dependencies.** `load_keys` (`keys.py:53–65`) accepts short lookup material, reused encryption/HMAC/signing material, missing active versions and omission of old versions still referenced by suppression rows. The missing-prior-version case silently stops matching erased opt-outs rather than freezing authority. `KeyStore.rotate` (`keys.py:36`) changes only a process dictionary, so a restart reloads the old file; `retire` checks dependencies without the common authority lock. This violates R26 and the precision contract. Validate key sizes/separation, active membership and all persisted dependency versions before enabling service; freeze when incomplete. Persist rotation atomically in the separately managed protected key store, retain prior keys for lookup only, and serialize retirement with restriction writes. Test startup with an erased old-key restriction and missing key, persisted rotation/restart, reused/short material and concurrent retirement/restriction creation.

6. **P1 — A reservation is not tied to a safe worst-case tariff.** `reserve` (`budget.py:26–35`) accepts arbitrary caller `amount` and only requires tariff version/currency/FX date. It never derives or checks amount from native unit price, quantity, tax, FX and contingency. For example amount 0 with those three metadata keys is accepted even if the provider operation costs money; `upper_micro_aud` exists but is not enforced at this boundary. This violates R19. Make an immutable validated tariff/operation quote the reservation input and compute the amount inside the ledger, requiring dated positive FX and all cost components. Use database transaction time for live reservation month; any synthetic clock injection must be explicit fixture scope. Test missing price/FX/tax, caller-understated amount, retries and genuinely free requests separately.

7. **P1 — The retention override also permits deleting suppression history.** The generic `immutable_evidence` trigger in `001_foundation.sql:124–132` returns OLD for every DELETE when `abr.retention_delete='on'`, and is attached to `suppression_event` and `audit_event`. A normal retention session can therefore erase the restrictions the restoration design depends on. R25/R29 explicitly prohibit routine retention from deleting suppression. Split ledger protection from finite-evidence deletion; suppression add/resolve rows must remain append-only even inside a retention session, with separately constrained reason-specific resolution. Prove `SET LOCAL abr.retention_delete='on'; DELETE FROM suppression_event ...` fails while permitted ordinary evidence deletion succeeds.

8. **P2 — Reviewed identity corroboration does not require independent references.** `Service.identity` (`service.py:145–148`) accepts any truthy `references` value with two boolean attribute claims. One reference or a string can therefore approve the fallback even though R16 requires at least two independently matching attributes with references/time. The exact-identifier path likewise trusts a caller's page identifier without binding a captured page/domain evidence reference. Reuse a typed evidence contract and require two distinct source references plus name and full-address/phone corroboration, or a captured exact validated source identifier on the specified domain. Test one-reference, duplicate-reference, wrong-domain capture and valid reviewer corroboration.
