# Independent durable enrichment review — 8 September 2026

Reviewed `enrich/worker.py`, fixture pipeline integration and migrations017/018 against R15/R19 and erasure requirements. Findings recorded before source owner fixes or new regression execution.

1. **P1: erasing a merged source profile loses the business-wide cooldown.** The cache query joins `enrichment_attempt` through its active `lead_entity`. Migration018 deliberately nulls the attempt's lead/candidate links on profile erasure while preserving paid receipts. A completed A attempt followed by A → B merge and A's 30-day deletion therefore disappears from B's family-cache query before the 90-day cooldown expires. B can run another lookup/crawl/verification despite the same reviewed business having a recent completed attempt. Preserve a minimal opaque group UUID on the attempt, and query the canonical family through that minimal identity after erasure; do not retain marketing profile fields to solve this.

2. **P2: resumed interrupted work crashes after ordinary payload expiry.** Retention clears `enrichment_operation.encrypted_result` at 90 days but retains completed stage/receipt authority. A still-blocked attempt resumes and directly decrypts every completed result, including NULL, in the prior-results comprehension. The worker raises instead of producing a controlled stale-evidence state. Detect absent/expired completed payloads before dispatch, emit an explicit review/refresh hold and preserve all existing operation/reservation IDs. No automatic repurchase or fabricated provider result should resolve the gap.

Positive source observations: billing is reserved and dispatched durably before provider calls; unknown dispatches reconcile using the same operation ID; transport runs outside control transactions; lease and policy are rechecked before result application; fixture pipeline permission comes from a separate explicit synthetic review adapter; provider output itself grants no basis. These observations do not close the findings above.

3. **P1: restore/key-incident quarantine is not checked by the worker.** `_allowed` evaluates policy, geography, lifecycle and suppression, but omits `system_state.restore_quarantine`, `system_state.key_compromised` and the in-memory key-store compromised flag. The contact/action gate correctly closes, while the durable worker can still reserve and make provider calls. Apply the same quarantine boundary before reservation and dispatch, and preserve it throughout restore until independent current budget/operation and key reconciliation is complete. A latest suppression ledger alone does not reconstruct paid operations after the backup watermark.

## Fix review — 9 September 2026

Source owner changed the worker to query family cooldowns by the preserved immutable `enrichment_attempt.group_id` (migration020), return `STAGE_EVIDENCE_EXPIRED` before decrypting erased payloads, and check all three quarantine states before reserve/dispatch/result application. Independent quarantine tests initially reproduced three failures (worker completed under each incident flag); after the fix all five independent worker cases pass. The first two tests were added while implementation/migration fixes were concurrently arriving, so their earlier transitional failures are not presented as reproduced original-behavior evidence.

Final combined independent worker/retention run: **39 passed in 153.25s** (five worker cases plus 34 retention cases), against actual isolated PostgreSQL16. Scoped Ruff and mypy passed. All three recorded worker findings are closed for the tested fixture behavior; post-backup billing reconciliation and live provider activation remain separate release work.
