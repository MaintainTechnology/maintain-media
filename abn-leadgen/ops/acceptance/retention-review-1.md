# Retention review 1 — 8 September 2026

Independent source review of `src/abr_engine/compliance/retention.py` against canonical R25/R26/R29 and the precision contract. Reviewed supporting migrations 001–007, current key authority and source artifact registration. Findings recorded before this reviewer begins a separate implementation/fix step. No live backup restore, remote deletion or production approval is claimed.

1. **P1: direct profile erasure bypasses the live retention gate.** `retention_run` refuses non-fixture execution but public `erase_profile` does not. An API or restore caller can invoke destructive erasure in pilot/production with no approved retention policy. Guard every destructive entry point, including replay-triggered erasure, and keep live capability pending until approval exists.

2. **P1: selected evidence is incomplete and its clock resets on deletion.** Archival includes contacts/provenance/basis/actions, but omits current identity, role relevance, licence review, wash and dated outcome evidence needed to explain a past decision. Seven-year expiry is calculated from erasure rather than the last relevant attempt/assessment. Capture the scoped selected evidence before removing active records and derive the deadline from the actual relevant timestamps; make repeated erasure/replay idempotent and avoid creating a fresh seven-year term.

3. **P1: conflicting replay rows can be silently ignored.** `ON CONFLICT DO NOTHING` for aliases/restrictions accepts a restored alias pointing to a different group or a reused immutable event ID with different content. The function still records a reconciled receipt. Compare immutable existing row content exactly, reject conflicts and leave the restore quarantined. Deletion-job state requires deliberate monotonic reconciliation, not a generic conflict ignore.

4. **P1: replay does not execute all overdue deletion before reconciliation.** It erases only tombstones with an already populated `primary_done_at`, leaving overdue 30-day suppression and 180-day unworked profiles from the restored backup untouched. Re-run due retention under the restore lock before claiming ledger reconciliation. Quarantine must remain set until independent physical-storage/remote/backup and release evidence is verified.

5. **P1: other retention classes are absent.** Raw ZIP 30-day, full analytical snapshot 90-day, ordinary page 90-day, minimal metrics 24-calendar-month and backup 35-day schedules have no implementation here. `artifact_manifest` has no authoritative retention kind or physical path/provider locator: a hashed staging object key cannot safely be translated into a local deletion path. Add an explicit typed finite schedule/planner, require authoritative inventory/storage adapters, and keep physical deletion and capacity/release evidence visibly pending. Expired accepted snapshots must invalidate the usable baseline; no indefinite current-pointer exemption.

6. **P2: scoped holds and evidence expiry need explicit handling.** Existing profile hold lookup recognises only `object_type='group'`; selected archive expiry checks the same broad scope. Support explicit archive/object holds with owner/reason/review time and surface overdue review rather than silently treating an expired review date as permission to delete. Do not infer a hold waiver.

Positive observations: suppression aliases and restrictions are not included in profile-deletion SQL; the dedicated immutable-restriction trigger is separate from the evidence-retention override; external CRM identity remains until remote confirmation; job state is `primary_complete`, never falsely backup/remote complete; replay intentionally leaves outbound quarantine enabled. These are useful controls but do not close the findings above.
